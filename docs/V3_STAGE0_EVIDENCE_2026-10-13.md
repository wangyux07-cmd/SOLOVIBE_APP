# V3-0 交付记录：固定试点与证据契约

> 日期：2026-10-13。范围仅为 V3-0；真实定位、返程路线、网页正文接入和实时库存仍属后续阶段。

## 已实现

- 冻结[上海 12 个试点查询](v3_pilot_shanghai.json)：咖啡、餐饮、景点、公园各 3 个。名单在查询前确定；空结果和错误不得从后续覆盖率分母中删除。星巴克官网早餐页作为**品牌级**来源候选列入，未标记为目标门店菜单。
- `backend/domain/evidence.py` 增加 VenueIdentity、SourceObservation、VenueClaim、FeasibilityCheck 和 ToolResult。来源观察保留 URL、范围、获取时间、结果、短证据/哈希；字段事实引用对应观察。分店级可用性判断核对来源 ID、POI ID、获取结果、状态和失效时间。搜索线索、品牌菜单、错店、过期优惠和高德登记时段冒充实时营业均不能通过。
- `backend/persistence/schema.sql` 增量加入 `venue_identity`、`source_observation`、`venue_claim` 三张表及索引。运行迁移后，脚本实际查询数据库并确认三表存在。现有会话、方案和动作表未改写。
- [运行 API 协议](../backend/API_PROTOCOL.md)明确了当前计划响应与后续 V3 证据响应的界限。V3-0 尚未把新 Claim 显示到前端，也没有声称已完成商家菜单或库存接入。

## 真实试点基线

运行 `python scripts/verify_v3_pilot.py --output docs/V3_PILOT_BASELINE_2026-10-13.json`，以本机已配置的真实高德 Key 逐一查询。完整原始候选与错误分类保存在[基线 JSON](V3_PILOT_BASELINE_2026-10-13.json)：**12 个查询，10 个返回至少一条候选，2 个空结果**。这只是搜索覆盖率，不是 10 家店完成身份验证。

其中咖啡 `cafe_01` 的查询同时返回“星巴克(港汇二店)”和其他港汇门店；餐饮 `dining_02` 返回的首项是另一家老乡鸡。直接选择首项会造成错店。`cafe_03` 和 `dining_01` 为空，应在后续阶段分析门店是否存在、名称是否变化或是否超出检索范围，不能悄悄换样本。

## 验证与边界

- 55 个 `tests/baseline` 用例通过，包括 V3 合同的错店、品牌菜单、缺价、过期优惠、失败结果，以及“登记时段不能当实时营业”“参考人均不能当具体商品价格”的测试。TypeScript 类型检查与前端生产构建通过。
- 真实 Supabase 增量迁移成功，`venue_identity`、`source_observation`、`venue_claim` 均返回 `true`。
- 本阶段未调用美团/大众点评商业接口，未取得任何实时座位或库存；没有为现有计划填充未经来源核实的价格。

下一步是 V3-1：用户主动定位、独立的返程路线、真实路线折线图，以及用去程、停留、返程和缓冲共同判断可用时间。完成后再进入 V3-2，把官网正文提取和分店匹配接入上述证据契约。
