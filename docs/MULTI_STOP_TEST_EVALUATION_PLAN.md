# SoloVibe 多站行程测试与量化评估规范

日期：2026-10-13。产品目标：针对用户的地点、时间、步行、预算和兴趣，在真实 POI 中生成**一条**有顺序的 2–3 站行程；明确要求晚餐时必须包含餐厅；每一段路线均来自高德，用户确认后获得逐段导航入口。保存、导航交接不等于到店或订位。餐厅代订只有在取得合规、可用的商家或平台写接口并验证真实回执后才可计入验收。

## 1. 被测边界与合同

| 层 | 输入 | 输出与失败合同 | 必测项目 |
| --- | --- | --- | --- |
| 状态提取 | 当前消息、近期消息、结构化快照 | 有原文依据的字段补丁；无依据不改状态 | 晚餐要求、取消晚餐、出发时刻、相对预算、跨轮更正、提示注入、非法类型 |
| POI 检索 | 城市、出发坐标、关键词 | 高德 POI ID、地址、坐标、类别、时间戳；空/失败分类 | 重复 POI、跨城、餐厅误判、错分店、无结果、403、429、超时、畸形响应 |
| 路线与排序 | 候选 POI、出发/返程点、约束 | 每段有真实方向、时长、距离、折线；最多一条完整方案 | 缺一段路线不得补直线；去返程不对称；晚餐时段；总步行/总时长；候选内最短可行顺序；无可行解 |
| 资料展示 | POI 详情 | 评分、人均、登记时段可为空；来源和查询时间可见 | 身份冲突降级；登记时段不得说成实时营业；未知价格不得变成预算已满足 |
| 动作执行 | 用户确认、方案版本 | 幂等保存或逐段高德链接；失败有原因 | 旧版本、重复点击、越权、断连恢复、过期、导航重查所有站点与路段 |
| 页面与部署 | 浏览器/容器环境 | 定位、修改、确认、刷新与删除流程 | 定位拒绝、手机尺寸、Cookie、同源 API、容器启动、密钥不进镜像与前端 |

## 2. 测试层级

1. **局部确定性测试**：状态补丁、餐厅分类、全排列排序、时钟/等待、上限边界、导航 URL。使用可控地图替身，断言算法行为，不把替身结果当真实地点指标。
2. **契约和故障测试**：模拟高德 200 空列表、错误 POI、路线缺段、403、429、超时和坏 JSON；检查统一失败分类、限次重试、不生成假方案、不重放已确认动作。验证 PostgreSQL JSON 方案、LangGraph checkpoint 与 API 响应可消费。
3. **真实依赖测试**：固定公开地标、真实高德 Key，记录逻辑调用数、失败类别和查询时间。模型提取单独测；地图排序单独测，避免把某层失败归因给另一层。
4. **端到端浏览器测试**：无模拟地执行“输入或授权定位→单条多站行程→调整条件→确认保存→确认逐段导航→刷新恢复→删除”。人工核对每段 URL 的目标地点；自动化只证明链接格式及打开请求，不能证明高德 App 接收或用户到站。
5. **稳定性与部署测试**：从清洁环境安装和迁移；Docker Compose 启动与重启；数据库短断线、供应商故障、并发请求、会话删除、备份恢复。Vercel 前端与实际后端同源代理需在部署后做一次真实浏览器验收。

## 3. 固定评测集与执行规则

正式评测建议至少 **40 个事先冻结的场景**：20 个预期可行的上海场景（不同地点、兴趣、晚餐与否、时间/步行档位），10 个边界场景（晚出发、过短时长、无餐厅、定位拒绝等），10 个依赖故障场景（用故障注入验证降级）。每个真实场景在不同时间重复至少 3 次；保留失败，不临时改题直到成功。冻结数据集版本、代码提交、配置类别、日期和时区。当前 `eval/itinerary_scenarios.json` 仅是 6 条**初始冒烟样本**，不能代表 40 条正式评测。

运行 `python scripts/evaluate_itinerary_live.py` 会调用真实高德并写入忽略提交的 `.runtime/evaluations/itinerary-live.json`。该脚本绕过 LLM，专门测 POI 与路线子系统；完整 Agent 的模型准确率、浏览器可用性和用户满意度必须单独评估。报告不含地址、坐标、POI 名称、用户消息或密钥。真实服务返回的结果会波动，因此每次都保存时间和场景分母。

2026-10-13 初始六场景地图子系统对照（同一场景集、真实高德、各运行一次）：优化前 4/6 生成方案，200 次逻辑地图调用，P95 26,016 ms；限制晚餐场景的候选景点数后仍为 4/6，178 次调用，P95 22,765 ms，6/6 结果与预期类别一致。两条未生成的场景分别是短步行和过晚晚餐的预设边界。调用数减少 22 次（11%）；P95 差异只是两次小样本观测，不能推断稳定提速。原始匿名汇总在本机忽略提交的 `.runtime/evaluations/itinerary-baseline-six.json` 与 `itinerary-final-six.json`；报告日期、场景集和分母在文件中保留。

## 4. 指标定义与判定

| 指标 | 精确定义 | 数据来源 |
| --- | --- | --- |
| 行程成功率 | 满足硬约束、至少 2 个真实站点、所有有向路段存在、必要晚餐已安排的场景数 / 全部场景数；同时报告可行集与边界集，不删失败样本 | 固定集 + 真实高德运行 |
| 餐厅覆盖率 | 明确要求晚餐且预期可行的场景中，最终含已匹配餐厅且到达时刻在晚餐窗口内的比例 | 方案 JSON + 人工抽核 |
| 路线完整率 | 具有有效高德路线证据的有向路段数 / 所有应有路段数；任一缺段时整条行程不发布 | POI/route 证据 |
| 约束违例率 | 总时间、总步行、站点数量、必选晚餐等硬约束被发布方案违反的次数 / 发布方案数；目标必须为 0 | 确定性检查 + 实测记录 |
| 候选内路径质量 | 在同一候选集和相同最大可行站数下，所选总步行时长与穷举最短可行时长的差；这不证明全城最优 | 固定地图替身 + 真实候选集 |
| 端到端成功率 | 预定义完整浏览器流程成功次数 / 全部执行次数；另列模型、地图、数据库、页面、动作失败 | Playwright + 服务端运行状态 |
| 响应延迟 | 从提交到可见方案的 P50/P95；地图子链路单独计时；报告样本数和冷/热启动条件 | 浏览器计时、运行 trace、评测脚本 |
| 外部调用与成本 | 单次方案的 DeepSeek 输入/输出 token、高德逻辑调用数、Tavily 调用数及按实际账单计算的费用；不把本地替身算入 | 模型 usage、计数器、账单 |
| 可恢复性 | 断连/重启后同一 request_id 不重复保存、旧方案无法确认、删除后业务与 checkpoint 均不存在 | 集成与真实数据库测试 |

建议每次迭代保存 `baseline → change → after` 同场景对照：版本、优化点、失败分布、成功率、P50/P95、调用数、成本及新增回归。不要把一次 1/1 成功写成 100% 稳定性，也不要把“地图链路成功”写成“模型整体准确率”。用户体验可另请志愿者做盲评并记录任务完成率、选中/改动原因与主观评分；不得编造真人使用数据。

## 5. 发布门槛与简历证据

局部契约、故障和安全测试须通过；正式固定集必须报告完整分母、错误分布及至少三轮真实结果；浏览器真链路、Docker 真构建/启动、实际公网 HTTPS 入口与数据库备份恢复分别留证。没有 Docker 引擎或 Vercel 后端地址时，把相应门槛标为**未验证**，不能用 `docker compose config` 或本地 Vite 构建代替。

简历只写能复现的指标。例如：“设计 LangGraph 状态机与结构化快照；在固定 N 个真实场景上，多站行程成功 X/N，P95 为 Y 秒，每次平均 Z 次地图逻辑调用；通过定向候选剪枝将调用数从 A 降到 B，同时保持成功率。”其中 N、X、Y、Z、A、B 都必须来自保存的原始运行记录。团队开发效率的提升还需任务前后耗时或交付周期数据；技术测试通过率不能直接推断为未来公司的效率增幅。
